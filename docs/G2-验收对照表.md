## 三、验收设计“交付前必答”

1. **改了哪些函数、签名/返回结构变没变？**  
   `_format.py` 的 6 个 `format_*`；签名全部不变（`reproduce_g2.py` 打印 `signatures: MATCH`，并有 `test_formatter_signatures_are_unchanged` 锁定）。返回仍是 `(str, list[str])` / `str`。
2. **16384 / 16385 边界？**  
   `Q4` = 16,384 B 完整返回；`Q5` = 16,385 B 截断为诊断文本 + warning，均 ≤16,384。
3. **中文/emoji 是否含 `\u`？`json.loads` 还成立吗？**  
   普通中文/emoji 不含 `\u`（`zh_readable` / `emoji_readable`）；`json.loads(整串)` 在**截断时从来就不成立**（上游即如此），正确解析是 `raw_decode`，所有 query 用例的 `json_ok` 均按此判定。
4. **dry_plan 加 cap 了吗？怎么标明不完整？**  
   加了；截断时闭合围栏并追加 `[truncated: incomplete SQL — X of Y bytes shown; do not execute as-is]`。
5. **before/after 原始数据在哪？**  
   `docs/evidence/{baseline,after}/results.json|csv`，每例完整 `content/<case>.txt`。
6. **pyarrow 真装了吗？**  
   26.0.1（`evidence/env/interpreter.txt`）。组件复验只需 pyarrow：仅装 pyarrow 的干净 venv 也跑出 before 15 / after 0（`evidence/reproduce-run-min-venv.txt`）。
7. **仓库内 `_format.py` 的 BASE 与 `CEA7814E…` 是否一致？**  
   基线副本 `docs/evidence/baseline/upstream_format_548eee3e.py` 的 SHA256 = `CEA7814ED569C223E1D5C997197020EF5C4A719DBD3121C32128F5B882B355C4`，与冻结值一致；`results.json` 的 `environment.modules.before.sha256` 记录同值。

## 四、验收设计“最可能判不通过的三点”

| 风险 | 本交付的处理 | 证据 |
|---|---|---|
| footer 从 content 挪进返回值 | **没挪**：footer 仍在 JSON 外，签名/返回不变；9 个兼容用例逐字节一致 | `signatures: MATCH`；`results.csv` 中 9 个 `IDENTICAL` |
| 中文改 `ensure_ascii=False` 但 cap 按字符数 | 所有 cap 判定都编码成 UTF-8 字节；恰好 16384 的用例是 ASCII，另有中文/emoji/随机表用例 | `_budget.utf8_bytes`；Q4/Q5；属性测试 `test_property_budget_holds_for_random_tables` |
| 只给 query 加 cap | query / dry_plan / recall / list_models / fetch_context / store 全部接入 | `D2`、`R2`、`L2`、`F2/F3`、`S2` 修后均 ≤16,384 且带标记 |
