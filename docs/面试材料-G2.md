# 面试材料（G2）：Wren SDK 工具输出预算

> 一句话：在固定上游 WrenAI 的 LangChain SDK 上，把 6 个 LLM 面向的工具输出统一到 16 KiB **UTF-8 字节**预算，中文不再被转义、超限时保留最大有序前缀并说明省略了什么；补了 25 个边界回归，真实 DuckDB 工具路径可复跑。
> （个人掌握程度请本人核对后再对外表述，不要把“能讲”写成“精通”。）

## 1. 问题

LLM 工具返回的 `content` 有 16 KiB 上限，但上游只在 `wren_query` 上做了截断，而且：

- 默认 `json.dumps(ensure_ascii=True)`：中文 6 B/字、emoji 12 B/字，可读性和预算双输；
- 截断按 25% 步进回退，每次整表重新 `dumps`，5000 行时保留 213 行却只用到 78.7% 预算，耗时 ~29 ms；
- `dry_plan` / `recall` / `list_models` / `store` **完全没有上限**（实测单次可到 27–44 KB，且不自报截断）；
- 空表但外部 `total_rows=100` 时只返回 `[]`，模型会当成“数据库没有数据”。

## 2. 上游行为（实跑，不是推测）

| 输入 | 上游输出 |
|---|---|
| 10 行中文 | 950 B，含 `\uXXXX` |
| 5000 短行 | 213 行 / 12,899 B（预算 78.7%），`showing 213 of 5000 rows` |
| 40 KB `dry_plan` SQL | 43,918 B，`warnings=[]` |
| 100 条长 recall | 27,371 B，`warnings=[]` |
| 300 个模型 | 30,344 B，`warnings=[]` |
| 空表 + `total_rows=100` | `"[]"`，无尾注、无 warning |
| 单行 16,385 B | 诊断文本，但写的是“row 1 alone **exceeds** 16384”——该行其实 16,383 B，超的是 JSON 框架 |

## 3. 我的改动

- 新增 `_budget.py`：`utf8_bytes`（ASCII 免编码）、`truncate_to_bytes`（按码点切）、`fit_text`（预留尾注）、`fit_blocks`（整块前缀 + 计数尾注）。
- `format_query_content`：快路径一次 `dumps`（`ensure_ascii=False`）；超限时逐行编码、贪心到“下一行放不下”为止；footer 计入预算；空表 + 外部 total 给出 `0 of N … external count`；单行过大时按真实字节数诊断。
- `format_dry_plan_content`：超限时闭合围栏 + `incomplete … do not execute as-is`。
- `format_fetch_context_content`：`full` 语义不变；`search` 改为整行保留 + `showing X of N context items`。
- `format_recall_content` / `format_store_content` / `format_list_models_content`：统一预算 + 计数尾注，表头保留。
- 契约不动：签名/返回 tuple/工具名/footer 位置（JSON 外）全部不变。

## 4. 为什么这样做

1. 预算必须按**字节**算：`ensure_ascii=False` 后按字符数限长，16384 个中文就是 49 KB。
2. 尾注/标记必须**先预留**再切正文，否则边界必超。
3. 最大前缀要**可证明**：`bytes + 2 + 下一行 > cap` ⇒ 再多一行必然装不下。
4. footer 留在 JSON 外是上游既有契约（`raw_decode` 用法），改了会静默破坏所有调用层——兼容性优先于“结构更漂亮”。
5. 性能靠“先估后切”：从 O(回退轮数 × 全表) 次编码降到每行一次。

## 5. 实际结果

| 指标 | 上游 | 现在 |
|---|---|---|
| 22 例硬门槛 | 15 项失败 | **0 项失败** |
| 小输入兼容 | — | 9 例逐字节一致（sha256） |
| 5000 行保留行 | 213 | **268（+25.8%）** |
| 1000 行中文保留行 | 135 | **224（+65.9%）** |
| 5000 行组件耗时（中位数） | 29.1 ms | **10.1 ms（2.9×）** |
| 真实 DuckDB 400 行 | 41 行 / 13,658 B | **87 行 / 16,231 B（+112% 行）** |
| SDK 测试 | — | **155 passed，2 skipped(slow)，0 failed** |

## 6. 边界（被问到时先讲这个）

- 只保证 `content` ≤ 16 KiB；外层信封 `data.rows` 不在 cap 内。
- 截断时仍是“JSON + 尾注”，`json.loads(整个 content)` 不成立，要用 `raw_decode`。
- 已在真实 DuckDB + `WrenToolkit` 工具调用层验证；**未**部署 Wren 平台，**未**跑真实 LLM agent，**未**跑 LanceDB memory 链路。
- 性能是组件级、固定数据/机器/重复数，不能推广成“Agent 提速”。
- 依赖用当前 PyPI 解析版本（wrenai 0.17.1），不是上游当年锁定版本。
