### 函数级改动

| 函数 | 上游行为 | 本次行为 |
|---|---|---|
| `format_query_content` | 整表 `json.dumps`（默认 `ensure_ascii=True`）；超限后按 25% 步进回退，每次全量重编码；footer 拼在 JSON 外，预留固定 64 B | 先按字节判断快路径；超限时逐行编码、**贪心取最大有序前缀**（下一行放不下即停）；footer 计入预算；空表 + 外部 `total_rows` 给出 `0 of N … external count`；单行过大时的诊断改为按真实字节数描述 |
| `format_dry_plan_content` | 直接包进 ` ```sql ` 围栏，无上限、无不完整标记 | 超限时闭合围栏并追加 `[truncated: incomplete SQL — X of Y bytes shown; do not execute as-is]` |
| `format_fetch_context_content` | `full` 已按字节截断；`search` 按字节截断，会切在行中间 | 共用 `fit_text`（`full` 语义不变）；`search` 按**整行**保留并给出 `showing X of N context items` |
| `format_recall_content` | 无上限 | 整条 NL→SQL 对保留到预算，尾注 `showing X of N past queries` |
| `format_store_content` | 无上限（超长 `nl` 可直接超 16 KiB） | 统一 cap，尾注 `truncated` |
| `format_list_models_content` | 无上限 | 表头保留、整模型行保留，尾注 `showing X of N models` |

### 为什么这样做

1. **字节，不是字符**：`ensure_ascii=False` 后若仍按字符数限长，16384 个纯中文 = 49 KB，直接破契约。所以所有判断都用 `len(s.encode("utf-8"))`（ASCII 走 `isascii()` 快路径）。
2. **预算必须含尾注**：截断标记本身占字节；先算正文再拼尾注的实现会在边界上超 1–100 B。`fit_text` 先预留 suffix，`fit_blocks` 每次候选都带 footer 一起判。
3. **最大前缀可证明**：保留 `k` 行后，若 `bytes + 2 + 下一行字节 > 16384`，则任何 `k+1` 行前缀都放不下——测试和复跑脚本都用这条判据，而不是“看起来接近上限”。
4. **契约不动**：footer 继续放在 JSON 外面（上游既有行为），调用层仍可用 `json.JSONDecoder.raw_decode` 拆正文/尾注；不改成结构化字段，避免所有调用层静默坏掉。
5. **先估后切**：上游每轮回退都整表 `dumps`（5000 行时约 10 次全量编码）；本次超限路径每行只编码一次，且一旦下一行放不下立即停止。

## 五、剩余限制与未验证项（别把 scope 说大）

1. **cap 只覆盖 `content` 字符串**。`wren_query` 信封里的 `data.rows` 仍是全部行（受 `MAX_QUERY_ROWS=1000` 约束），所以“整条 ToolMessage/整个 LLM 上下文 ≤ 16 KiB”**不成立**，本次不宣称。
2. **W8 契约保持原样**：截断时 content 仍是“JSON 正文 + JSON 外尾注”，`json.loads(整个 content)` 依旧失败；正确用法是 `raw_decode`。没有改成结构化字段，因此调用层无需改动。
3. **空表 + 外部 total 会置 `warnings`**，于是信封 `data.content_truncated=True`，尽管没有真的截断。这是有意让调用方注意到“数字对不上”；`data.row_count` 仍是权威值。若后续认为该标志语义应收窄，可单独讨论。
4. **memory 工具未跑真实 LanceDB**：`wren_recall_queries` / `wren_fetch_context` 的真实向量检索属于 `slow`（需 sentence-transformers），按卡未安装 memory extra；这两个格式化函数由组件用例 + 单测覆盖，不是“整链路已验”。
5. **依赖是当前索引解析结果**（wrenai 0.17.1、langchain 1.4.9…），不是上游当年锁定版本；上游测试在此环境全绿，但不同依赖版本可能改变测试集合。
6. **未部署 Wren 平台/数据库服务**，未跑真实 LLM agent，未调用付费模型，未安装大模型。
7. **未向维护者发 PR/消息**，没有远端仓库链接；本机演示已完成，发布需总控看 diff 后决定。
8. 单行超过预算时仍按上游设计**整行不展示**（诊断文本），不是“截半个 JSON”；若未来希望单行值内截断，需要新的契约设计。

## 六、学习点（3–5 条，供本人核实掌握程度）

1. **“16 KiB”必须先问是字节还是字符**：同一段中文，`ensure_ascii=True` 是 6 B/字、直出是 3 B/字，差 2 倍预算；emoji 更夸张（12 B vs 4 B）。改编码和改预算必须同时做，否则 cap 形同虚设。
2. **截断的正确性是可以证明的**：保留最大前缀的判据是“再多一行必然放不下”，而且尾注/标记本身要计入预算——先算正文再拼尾注，边界上必超。
3. **返回契约比“看起来更好”重要**：`(str, warnings)`、footer 位置、工具名都不能动；把 footer 挪进 JSON 会让所有调用层静默失效。用签名测试 + 逐字节兼容用例锁住它。
4. **性能问题常常是重复劳动**：上游每次回退都整表 `dumps`，改成“每行编码一次 + 贪心停止”，超限路径约快 3×，而代码并没有变复杂。
5. **scope 要写在交付里**：组件通过 ≠ 平台通过；cap 覆盖 content ≠ 覆盖整个信封。把未验证项列清楚，比多写一句“已提速”更值钱。
